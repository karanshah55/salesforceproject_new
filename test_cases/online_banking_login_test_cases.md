## 1. Requirement List

The requirement IDs are taken unchanged from the Test Plan requirement register.

| ID | Type | Requirement | Plan priority focus |
|---|---|---|---|
| FR-01 | Functional | Registered users can log in using username and password | High |
| FR-02 | Functional | Username must be a valid email address | Medium |
| FR-03 | Functional | Password must contain at least 8 characters, at least 1 uppercase letter and at least 1 number | High (R-10) |
| FR-04 | Functional | After successful login the user is redirected to the Dashboard and the last login timestamp is updated | Medium |
| FR-05 | Functional | After 5 consecutive failed login attempts the account is locked for 15 minutes | Highest (R-02, R-03, R-11) |
| FR-06 | Functional | A "Forgot Password" link is available on the login page | Medium |
| FR-07 | Functional | The user session expires after 15 minutes of inactivity | Highest (R-04, R-08) |
| FR-08 | Functional / Security | Error messages do not reveal whether the username or the password was incorrect | Highest (R-01) |
| NFR-01 | Performance | Login response time is less than 3 seconds | Highest (R-05, R-06) |
| NFR-02 | Scalability | The system supports 5,000 concurrent users | Highest (R-05, R-06) |
| NFR-03 | Compatibility | The login page works on Chrome, Firefox, Edge and Safari | High (R-07) |

| Implicit requirement | Parent |

| Credentials never appear in URLs, browser storage or logs (R-14) | FR-01, FR-06 |

| Technical errors (stack traces, service names) are never shown to the user | FR-08 |
| Login form is accessible (labels, keyboard, screen reader announcements) | FR-01, FR-06, FR-08 |

## 2. Assumptions and Open Questions

### Assumptions

All Test Plan assumptions A-01 to A-19 apply. The following are the ones that shape these test cases, plus test-case level assumptions (TA-xx).

| # | Assumption |
|---|---|
| A-01 | Web UI plus REST/JSON auth API (`POST /auth/login`, `POST /auth/logout`, session/token refresh). Endpoint names in the test cases are placeholders until the API specification (D-03) is received |
| A-05 | FR-03 password rules are enforced when a password is set (registration, reset, change, provisioning). On the login screen the system only authenticates and returns the generic FR-08 error. Rule tests therefore run against the password set/reset function, and login-screen tests check that rule details are never disclosed |
| A-06 | Failed attempts are counted per account and a successful login resets the counter |
| A-07 | The lock lifts automatically after 15 minutes, without admin action |
| A-08 | Only user-initiated requests count as activity; background polling does not extend the session |
| A-09 | NFR-01 is measured at p95, from the click on Login to Dashboard rendered, under NFR-02 load |
| A-10 | NFR-02 means 5,000 concurrently authenticated, active sessions |
| A-11 | NFR-03 covers the latest and latest-1 desktop versions of each browser; mobile is out of scope |
| A-14 | No MFA in this release |
| A-17 | Lockout and session timeouts can be shortened by configuration in QA; every timer case is also run at least once at the real 15 minute value in Staging (EX-08) |
| A-18 | QA has read access to the database and application logs |
| TA-01 | Default precondition for every UI case (unless stated otherwise): the QA environment login page is reachable over HTTPS, the browser has cleared cookies/storage, and the test account is active, unlocked, with a failed-attempt counter of 0 |
| TA-02 | Lockout cases use dedicated, resettable accounts from the lockout pool (`lock01@testbank.com` ... `lock30@testbank.com`) so parallel runs cannot contaminate each other (R-11) |
| TA-03 | The generic error message is referred to as `<GENERIC_ERROR>` (for example "Invalid username or password") until the business confirms the wording (Q-12). The lock message is `<LOCK_MESSAGE>` |
| TA-04 | Timer boundaries are judged as follows: 14:59 elapsed means "not yet expired/unlocked", 15:00 or more means "expired/unlocked". The requirement says "for 15 minutes" and "after 15 minutes", so exactly 15:00 is treated as the first moment of expiry/unlock; a tolerance of +/- 5 seconds is accepted for real-time tests unless the business sets another value |
| TA-05 | NFR-01 pass criterion is strictly less than 3.000 s at p95; a p95 of 3.000 s or more is a fail |
| TA-06 | Email maximum length follows RFC 5321: 64 characters for the local part and 254 characters in total |
| TA-07 | All test data is synthetic and obviously fake (domain `testbank.com`, passwords such as `Passw0rd1`). Real credentials for QA accounts are held in the secrets store; the values shown here are illustrative |
| TA-08 | The Online Banking Portal is a different system from the Salesforce application in this repository, so no existing automated test covers any of these cases. "Automation Candidate = Yes" means the case can be automated with the repo's Playwright/pytest POM framework (UI), a REST client following the `api/` pattern (API), or the load tool chosen in the Test Plan (performance). It does not mean the case is already automated |
